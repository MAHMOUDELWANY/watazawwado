# P2 findings (end-to-end workflows, started 2026-11-10)

Format: [../RULES.md](../RULES.md#findings). Screenshots in [shots/p2/](shots/p2/). Specs: `e2e/*.api.spec.ts`

## P2-001 · Medium · tooling, MSG-04, LES-02, INT-01, LES-03 · all roles · local servers only · open (owner)
`.env.vercel` (from `vercel env pull`) holds the text `[SENSITIVE]` instead of the value for every variable marked
sensitive on Vercel: `BREVO_API_KEY`, `GEMINI_API_KEY`, `ZOOM_*`, `GOOGLE_CLIENT_ID/SECRET`, `CRON_SECRET`,
`VAPID_PRIVATE_KEY`, `STRIPE_WEBHOOK_SECRET`, `NOTIFICATION_*`. The main checkout's `.env` overrides none of them.
- Effect on every `qa-pN` server: no email is sent (Brevo answers 401), no Zoom meeting, no AI intake or drafts, no
  Google Calendar connect, no push. docs/testing/RULES.md said "emails really arrive"; they do not.
- So P2 could not check a real inbox, a real Zoom link or the AI chat end to end. What was checked instead: the
  rows the server writes (reminders, notices, jobs) and that a failing provider never breaks the booking.
- Also: the main checkout's `package-lock.json` is older than `package.json` (no Playwright), so `npm ci` from the
  RULES.md first steps fails. P2 used the P1 worktree's lock file.
- Proposed: the owner copies the real values of those variables into the main checkout's `.env` (test-mode keys
  where the provider has them), or marks which ones may stay off locally; refresh the lock file in the main
  checkout (`npm install`) and fix the RULES.md first steps.

## P2-002 · Low · MSG-02, MSG-03 · all roles · fixed
A malformed `VAPID_PRIVATE_KEY` made `pushConfigured()` throw inside `notifyUser`, after the on-site notice was
saved but before the email part ran: every notice of a "push kind" (new student, lesson booked, chat...) lost its
email. Seen locally because of P2-001; production has a valid key, so this is hardening.
- Fix: `server/notifications/push.ts` switches push off and logs once instead of throwing.
  Test: `test/nx-09-push.test.ts`.

## P2-003 · High · BOOK-01, AUTH-02 · P · any device, AR + EN · production too · fixed
The second child of a family cannot book their free trial: the server answers 500 "Failed to create booking
reservation. Please try again." Rule (RULES.md §2, 2026-11-07): every child gets their own free trial.
- Steps: family account with two children; book the free trial for one child; book the free trial for the other.
- Expected: second trial confirmed. Actual: 500 for ever (until the first child's trial is cancelled).
- Cause: the database still has `idx_bookings_one_trial_email` and `idx_bookings_one_trial_whatsapp`
  (migration 20260905000001): one active or completed trial per contact email / WhatsApp. Every child's booking
  carries the parent's email, so the second insert violates the index. The 2026-11-07 change only edited the
  server's pre-check; its test reads the source text and never inserts two trials.
- Same root: a real double click on "Book" got 500 instead of "you already have a free trial".
- Fix: migration `20261110000210_one_trial_per_learner.sql` (one trial per learner: unique on `student_id`; the
  email / WhatsApp indexes stay only for rows with no learner), and `/api/bookings/create` answers 400 for a
  duplicate trial and 409 for a time taken in the same instant, instead of 500.
  Test: `e2e/booking.api.spec.ts` "each child gets their own trial" (failed with 500 before the fix).

## P2-004 · Medium · BOOK-02, BOOK-07 · S P · any device · production too · fixed
One learner could be booked into two lessons at the same minute with two different teachers (the overlap rule in
the database is per teacher). A parent tapping the wrong child, or booking the same child twice from two tabs
with a different teacher picked, ended with two held or confirmed lessons at one time.
- Steps: the teen has a trial with teacher-1 at 07:00; book a paid lesson for the teen at 07:00 with teacher-2.
- Expected: refused. Actual: 201, a second lesson at the same time.
- Fix: `learnerHasLessonAt` in api/index.ts, checked by `/api/bookings/create` and the student reschedule
  (409 `LEARNER_BUSY`, Arabic text in `bookingErrors.ts`). Test: `e2e/booking.api.spec.ts`
  "a learner cannot be in two lessons at the same time" (201 before the fix).
