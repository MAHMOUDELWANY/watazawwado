# P2 findings (end-to-end workflows, started 2026-11-10)

Format: [../RULES.md](../RULES.md#findings). Screenshots in [shots/p2/](shots/p2/). Specs: `e2e/*.api.spec.ts`
(server + database, run once) and `e2e/*.spec.ts` (browser, phone/desktop x Arabic/English).

## P2-001 · Medium · tooling, MSG-04, LES-02, INT-01, LES-03 · all roles · local servers only · open (owner)
`.env.vercel` (from `vercel env pull`) holds the text `[SENSITIVE]` instead of the value for every variable marked
sensitive on Vercel: `BREVO_API_KEY`, `GEMINI_API_KEY`, `ZOOM_*`, `GOOGLE_CLIENT_ID/SECRET`, `CRON_SECRET`,
`VAPID_PRIVATE_KEY`, `STRIPE_WEBHOOK_SECRET`, `NOTIFICATION_*`. The main checkout's `.env` overrides none of them.
- Effect on every `qa-pN` server: no email is sent (Brevo answers 401), no Zoom meeting, no AI intake or drafts, no
  Google Calendar connect, no push. docs/testing/RULES.md said "emails really arrive"; they do not.
- So P2 could not check a real inbox, a real Zoom link or the AI chat end to end. What was checked instead: the
  rows the server writes (reminders, notices, jobs) and that a failing provider never breaks the booking.
- Also: the main checkout's `package-lock.json` is older than `package.json` (no Playwright), so `npm ci` from the
  RULES.md first steps fails. P2 used the P1 worktree's lock file.
- Proposed: the owner copies the real values of those variables into the main checkout's `.env` (test-mode keys
  where the provider has them), or marks which ones may stay off locally; refresh the lock file in the main
  checkout (`npm install`) and fix the RULES.md first steps.

## P2-002 · Low · MSG-02, MSG-03 · all roles · fixed
A malformed `VAPID_PRIVATE_KEY` made `pushConfigured()` throw inside `notifyUser`, after the on-site notice was
saved but before the email part ran: every notice of a "push kind" (new student, lesson booked, chat...) lost its
email. Seen locally because of P2-001; production has a valid key, so this is hardening.
- Fix: `server/notifications/push.ts` switches push off and logs once instead of throwing.
  Test: `test/nx-09-push.test.ts`.

## P2-003 · High · BOOK-01, AUTH-02 · P · any device, AR + EN · production too · fix written, **migration waiting for the owner**
The second child of a family cannot book their free trial: the server answers 500 "Failed to create booking
reservation. Please try again." Rule (RULES.md §2, 2026-11-07): every child gets their own free trial.
- Steps: family account with two children; book the free trial for one child; book the free trial for the other.
- Expected: second trial confirmed. Actual: 500 for ever (until the first child's trial is cancelled).
- Cause: the database still has `idx_bookings_one_trial_email` and `idx_bookings_one_trial_whatsapp`
  (migration 20260905000001): one active or completed trial per contact email / WhatsApp. Every child's booking
  carries the parent's email, so the second insert violates the index. The 2026-11-07 change only edited the
  server's pre-check; its test reads the source text and never inserts two trials.
- Same root: a real double click on "Book" got 500 instead of "you already have a free trial".
- Fix: migration `20261110000210_one_trial_per_learner.sql` (one trial per learner: unique on `student_id`; the
  email / WhatsApp indexes stay only for rows with no learner), and `/api/bookings/create` answers 400 for a
  duplicate trial and 409 for a time taken in the same instant, instead of 500.
  Test: `e2e/booking.api.spec.ts` "each child gets their own trial" (failed with 500 before the fix).
- State on 2026-11-11: the route change is in (the family now reads "you already have a free trial" instead of a
  500, which is still the wrong answer for a second child). The migration was **not applied**: the tool call to
  apply it to production was declined in this session. Until it is applied this test stays red and the second
  child of every family is blocked. No trial rows exist in production yet, so the index change is safe.

## P2-004 · Medium · BOOK-02, BOOK-07 · S P · any device · production too · fixed
One learner could be booked into two lessons at the same minute with two different teachers (the overlap rule in
the database is per teacher). A parent tapping the wrong child, or booking the same child twice from two tabs
with a different teacher picked, ended with two held or confirmed lessons at one time.
- Steps: the teen has a trial with teacher-1 at 07:00; book a paid lesson for the teen at 07:00 with teacher-2.
- Expected: refused. Actual: 201, a second lesson at the same time.
- Fix: `learnerHasLessonAt` in api/index.ts, checked by `/api/bookings/create` and the student reschedule
  (409 `LEARNER_BUSY`, Arabic text in `bookingErrors.ts`). Test: `e2e/booking.api.spec.ts`
  "a learner cannot be in two lessons at the same time" (201 before the fix).

## P2-005 · High · BOOK-12, BOOK-03 · A (hurts S P) · desktop + phone · production too · fixed
The admin's "Record payment" form saves the payment as **Confirmed** by default, and the server stored that row
without confirming the lesson. The lesson stayed an unpaid hold, so 35 minutes later the hold expired and the
lesson was cancelled, with a confirmed payment on record and no reminders, meeting or notice for the family.
- Steps: a learner books a paid lesson and has not paid online; the admin opens the booking → Record payment →
  Save (status "Confirmed" is preselected).
- Expected: lesson confirmed, like the Confirm button. Actual: payment `confirmed`, booking still `pending`.
- Suspected: api/index.ts `POST /api/dashboard/payments` inserted the row as given; only
  `/payments/:id/confirm` ran `verify_payment_atomic`.
- Fix: a payment recorded as received for a lesson that still waits for payment goes through
  `verify_payment_atomic` (lesson confirmed, meeting and reminders queued, family notified); if the lesson
  stopped waiting meanwhile the admin gets 409 and nothing is recorded. Recording a payment for an already
  confirmed lesson (pay later) is unchanged. Test: `e2e/paid-lifecycle.api.spec.ts` "a payment recorded as
  already confirmed also confirms its lesson" (booking stayed `pending` before the fix).

## P2-006 · Low · AUTH-04 · S P · every learner page · open
Every page of the learner portal calls `GET /api/dashboard/me` (the staff API) to find out whether the account is
staff, and gets 403. The browser console shows a red error on every page load of every family.
- Suspected: src/lib/auth.tsx `checkServerTeacherAuthDetails`.
- Proposed: answer 200 `{ isTeacher: false }` from a neutral endpoint (or skip the call when the account has a
  `students` row), so real errors stand out in the console and in monitoring.

## P2-007 · Medium · AUTH-04, LES-01, BOOK-03 · S P T A · phone + desktop, AR + EN · fixed
Zad's tour opened by itself on whatever page the account first landed on in a browser, covered it, and its first
step sent the person to the home page. A parent who opens a link to "Book", a learner who opens the lesson room
on a new phone two minutes before the lesson, or anyone returning from checkout on a new device was pulled away.
- Steps: new browser, sign in, open `/student/book` directly. Screenshot: `shots/p2/P2-007-tour-over-book-phone-ar.png`.
- Expected: the booking page. Actual: the home page under the tour card.
- Fix: the tour opens by itself only on the area's home page (`isTourHome` in src/lib/tours.ts, used by
  StudentApp and DashboardApp); the "Quick tour" button still opens it anywhere. Test: `test/zad-tours.test.ts`.

## P2-008 · Medium · BOOK-12 · A · open (owner decides)
The admin can record and confirm any amount for a lesson: USD 0.50 confirms a USD 4.50 lesson with no warning.
A typing slip (0.45 for 4.5) passes silently and the books are wrong. Other currencies are legitimate (a GBP
transfer), so the server cannot simply compare numbers.
- Proposed: in the Record payment form, when the currency is USD and the amount is below the lesson price, ask
  "This is less than the lesson price (USD 4.50). Record it anyway?" and store that the admin confirmed it.
  Test kept as an expected failure: `e2e/paid-lifecycle.api.spec.ts` "a payment for less than the lesson price".

## P2-009 · High · BOOK-07 (teacher), BOOK-11 (admin cancel) · T A (hurts S P) · production too · fixed
Two database functions the dashboard relies on do not exist in the production database:
`teacher_reschedule_booking` and `teacher_cancel_booking` (defined in migration 20260908000008, absent from
`pg_proc`; every other function the server calls is present). So in production:
- a teacher moving a lesson ("Move lesson" with a reason) always gets 500 "Failed to reschedule booking.";
- the super admin cancelling a lesson from the dashboard always gets 500 "Failed to cancel booking.".
RULES.md §1 makes these the only way a teacher changes a lesson and the only way a lesson is cancelled by us.
- Steps: as a teacher, open an upcoming lesson → move it to another day with a reason.
- Also wrong in the old function: a paid lesson cancelled by the academy was only marked cancelled; the family
  kept neither a credit nor a refund (RULES.md §2: they choose a new time, a credit or a refund).
- Fix (code only, no migration needed): `PATCH /api/dashboard/bookings/:id` moves and cancels in the route.
  A move checks the learner's other lessons too (P2-004). An academy cancel of a paid lesson goes through
  `student_cancel_paid_lesson_to_credit` and marks the credit `platform_cancel` (never counted toward the refund
  limit); other lessons are cancelled with their reminders and their Zoom/calendar job, and a lesson paid from
  the balance gets the balance back. Tests: `e2e/teacher.api.spec.ts` "a teacher moves a lesson with a reason"
  and "only the super admin cancels" (both 500 before the fix).
- For the owner: something removed these two functions from the database outside the migrations. Worth a look
  at the Supabase dashboard history; P3 should compare every table, policy and function with the migrations.

## P2-011 · Medium · MSG-01, INT-06 · P S · fixed
After a teacher change the chat with the previous teacher is closed. When the admin later put the learner back
with that teacher from Students → Assigned teacher, the chat stayed closed: the family could not write to its
own current teacher ("This conversation is closed").
- Fix: the direct assign route reopens the chat with the teacher it assigns (api/index.ts `assign-teacher`).
  Test: `e2e/family.api.spec.ts` "the admin can also assign a teacher directly".
- Still open (owner decides): after an approved change a free trial stays with the previous teacher (policy), but
  the family's chat with that teacher is already read-only, so they cannot write to the teacher of a lesson they
  still have. Proposed: keep the chat open until the last booked lesson with that teacher has passed.

## P2-012 · Medium · BOOK-01, BOOK-02 · S P · phone + desktop, AR + EN · open (owner decides)
"Pick a time" opens with the first day and the **first time already selected**, and Continue is enabled. For a UK
family that first time is 04:00 (the teacher's 06:00 Cairo). Someone who taps Continue too fast books a 4 a.m.
trial; a trial can then be moved only once, and cancelling it costs a 48-hour wait. When the list reloads and a
suggested time is gone, the form also swaps in another time silently (`StepDateTime.tsx` "fallback").
- Screenshot: `shots/p2/P2-012-first-time-preselected-desktop-en.png`.
- Proposed: select the first day only; no time until the family taps one (Continue stays disabled), and when a
  chosen time disappears say so instead of replacing it. Also consider hiding hours before 06:00 in the learner's
  zone behind "show early hours".

## P2-016 · Low · design, RTL · P · AR · fixed

## P2-019 · Low · PKG-02 · S P · open
Every tap on "Choose package" creates another `pending_payment` package row; two quick taps leave two unpaid
packages for the same learner, and abandoned ones are never cleaned up. Nothing is charged, but the wallet and
the admin list fill with dead rows. Proposed: reuse the account's open unpaid row for the same package and
learner (answer 200 with it), and expire unpaid rows after a day.
Test kept as an expected failure: `e2e/more-flows.api.spec.ts` "a second tap on Choose package".

## P2-020 · Medium · BOOK-01, AUTH-02 · P · fixed
A parent who only follows their children could send a booking with no child chosen: the server booked it for the
parent's own row, which has no teacher (P1-002), so the lesson went to whichever teacher the site picks by
default, possibly one the family never chose. The form already stops this; the server did not.
- Fix: `/api/bookings/create` answers 400 `LEARNER_REQUIRED` ("Please choose which child this lesson is for")
  for such an account, Arabic text in `bookingErrors.ts`. Tests: `e2e/booking.api.spec.ts` "a parent cannot book
  for a learner outside the family", `e2e/booking-ui.spec.ts` "a parent books the trial for the child they picked".
